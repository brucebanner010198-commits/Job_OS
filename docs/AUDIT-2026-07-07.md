# Job OS — Full Product Audit (2026-07-07)

Scope: completeness, resilience, reliability, maintainability, and UI/UX quality for real-world local hosting. Evidence-based; file references point to code as of today.

---

## 1. Executive summary

The foundations are better than most local-first side projects. Failure isolation is real (`Promise.allSettled` sources, `safeDb`, lazy Prisma proxy, DB banner), security primitives are sound (SSRF guard, constant-time token compare, LAN gating, OpenRouter ZDR), the setup wizard and dark mode are genuine, and the scheduler is idempotent.

The product is **not yet dependable or shippable** for three reasons:

1. **It hangs quietly instead of failing loudly.** No timeouts on job-source fetches, AI calls, or the pg pool; no overlap locks; no backoff. A slow vendor stalls the whole discovery cycle indefinitely.
2. **The desktop/launch story is broken.** The Tauri build bundles the wrong directory (`.next/standalone` vs actual output `.next-build/standalone`), assumes `node` on PATH (GUI apps don't have it), has no port-conflict handling, and there is no update mechanism at all.
3. **The UI still reads as a developer tool in key places.** One global spinner instead of skeletons, sample data silently substituting for empty states, `npm run db:up` shown to end users in a banner, and 13 of ~20 destinations hidden in a collapsed "Settings & tools" accordion.

Also: **live API keys (OpenRouter, Gmail client secret) are sitting in cleartext in `.env` in the working tree.** Rotate them.

## 2. Backend / architecture findings

### Robust (keep)
- SSRF guard used by `safeFetch` (`lib/security/url.ts`, `lib/brief/fetch-utils.ts`): 12s abort, 50KB cap, never throws. This is the correct template — it simply wasn't propagated.
- Job discovery failure-isolated per source (`lib/jobs/sources/index.ts:37-45`).
- Graceful DB degradation: `lib/safe.ts`, lazy Pool proxy (`lib/db.ts:48`), 5s-cached health (`lib/db-health.ts`).
- Recency anchored to `firstSeenAt`, not vendor-claimed dates — deliberate anti-manipulation.
- Scheduler: pure planner + watermarks, garbled watermark fails safe to "run".
- `chatJson` schema-validates AI output and retries once with a corrective nudge.

### Top backend issues (ranked)
1. **HIGH — No timeouts on live job sources** (`remotive.ts:68`, `remoteok.ts:41`, `arbeitnow.ts:47`, `jobicy.ts`, `jsearch.ts:67`). One hung vendor stalls the entire `discover()` because `allSettled` waits for all. Fix: shared `fetchWithTimeout` (reuse `safeFetch` pattern).
2. **HIGH — No default timeout on `chat()`/`embedText()`** (`lib/ai/openrouter.ts:71`, `lib/ai/embeddings.ts:39`) on the per-job scoring hot path. `probeOpenRouter` already shows the right pattern (`AbortSignal.timeout(10_000)`).
3. **HIGH — Serial ingest with triple-computed embeddings** (`lib/jobs/service.ts:73-135`, `lib/scoring/embedding-relevance.ts:158,183,192`). Hundreds of sequential untimed API calls per 50–250 job batch. Fix: cache the job embedding once, batch/parallelize with a concurrency limit.
4. **HIGH — pg Pool: no `max`, no timeouts, and no `pool.on('error')` handler** (`lib/db.ts:24`). A Postgres restart emits an unhandled `'error'` event that can crash the Node process. `/api/health` itself can hang (`db-health.ts:44` has no timeout).
5. **MED-HIGH — Secrets file lost-update race**: `saveKeys` is read-modify-write with no lock (`lib/secrets/file-store.ts:23-48`). Two concurrent saves silently drop a key.
6. **MED-HIGH — No overlap guard**: launchd catchup can overlap a still-running previous run or a user-triggered discover. Data stays correct (idempotent upserts) but API spend doubles and TOCTOU exists on `firstSeenAt`. Fix: pidfile/DB advisory lock.
7. **MED — Watermark advances on failure with no backoff or alerting** (`scripts/run-catchup.ts:48`). Persistent failures (revoked Gmail token) are silently masked.
8. **MED — Job data never expires**: `listQueue` returns all non-excluded jobs regardless of age; nothing prunes dead listings or re-verifies URLs. Brief-facts freshness logic (`lib/brief/volatile.ts:113`) doesn't apply to jobs. RemoteOK also fetched with no User-Agent (commonly 403s).
9. **MED — Input validation covers only ~3 server actions** (`lib/validation/action-schemas.ts`). `saveAnswersAction`, `prepareApplicationAction`, `discoverJobsAction` and most brief/goals/resume/warm actions take raw input.
10. **LOW-MED — Tokens in query strings**: Gmail push webhook `?token=` (`app/api/gmail/push/route.ts:24`) and legacy `?token=` access path (`lib/auth/access.ts:68`). Webhook also always returns 204, so push failures are invisible.

Additional: uncapped 100-way Gmail fan-out (`lib/gmail/source-live.ts:64,91`); vendor dates stored without validity checks; no circuit breaker anywhere — a hard-down dependency is re-tried at full timeout cost every wake.

**Systemic diagnosis:** the good pattern (timeout + abort + never-throw) exists in one file and was never made a shared utility. Fixing issues 1–4 with one shared HTTP wrapper plus pool config removes most of the real-world resilience risk.

## 3. Install / launch / update / lifecycle findings

### How launch works today
Docker Postgres (`db:up`) → prisma migrate → `next dev`/`next start` on hardcoded :3000. Optional launchd agents (`install-agents.ts`) run catchup every 30 min and daily encrypted backups. The Tauri desktop shell is an explicit scaffold.

### Top lifecycle issues (ranked)
1. **CRITICAL — Live secrets in cleartext `.env`** (real OpenRouter key, Gmail client secret). Not in git, but active. Rotate now; keep only placeholders in the tree.
2. **CRITICAL — Tauri path mismatch**: `tauri.conf.json` bundles `../.next/standalone` but `build-standalone.sh` outputs `.next-build/standalone`. Desktop build ships a missing/stale server → blank window.
3. **CRITICAL (desktop) — No bundled Node runtime**: `main.rs` spawns `node` from PATH with stdout/stderr nulled. GUI-launched apps have minimal PATH → silent no-start, no error surfaced.
4. **HIGH — No port-conflict handling**: 3000 and 5432 hardcoded everywhere (incl. OAuth redirect URIs). Common failure, zero recovery.
5. **HIGH — No update mechanism**: no Tauri updater, no version check, migrations not auto-applied on launch — a `git pull` update silently runs new code on an old schema.
6. **HIGH — Contradictory migration guidance**: docs say `migrate deploy`; DB banner and `db:migrate` say `migrate dev` (wrong for fresh installs; can prompt for shadow DB / reset).
7. **MED-HIGH — launchd log dir never created**: plists write to nonexistent `.logs/` → agents fail or lose all diagnostics.
8. **MED — No preflight**: no `engines` field, no `.nvmrc`, no "is Docker running" check. Failures surface only as runtime 503s.
9. **MED — Weak first-run bootstrap**: manual `db:seed`, default `you@example.com` primary user, nothing forces setup/key verification.
10. **MED — Passive DB recovery**: single global pool, no reconnect backoff after Postgres restart.

Strengths to preserve: `.next` vs `.next-build` split (prevents cache corruption), idempotent catchup/backup, LAN gating in `proxy.ts`.

## 4. Frontend / UI-UX findings

### Strong
Systematic DB-down resilience on every page; three-layer error boundaries (incl. inline-styled `global-error.tsx`); real accessibility baseline (focus rings, aria attributes, 44px targets); complete dark-mode token set; good 4-step setup wizard.

### Top UI/UX issues (ranked by user impact)
1. **Loading feedback is one bare spinner.** Single `app/(app)/loading.tsx`; zero skeletons repo-wide, while every page is `force-dynamic` with 3–4 blocking queries. Biggest "feels unfinished" signal.
2. **Sample data masquerades as real data.** `jobs/page.tsx:51` shows fixture jobs whenever the queue is empty — a healthy-but-empty DB shows fake postings with only a small muted notice. Erodes trust; a real empty state is never shown.
3. **Empty states are nearly absent** (one found, in `track/applied-stage.tsx`). First-run users hit blank lists with no guidance or CTA.
4. **Action feedback is inconsistent**: `ActionFeedback`/`useActionFeedback` used by only 4 components; others roll their own or give none. No global toast system.
5. **No `prefers-reduced-motion` support** despite spins, pulses, and scale transitions (WCAG 2.3.3 gap).
6. **Navigation buries the product**: 13 of ~20 destinations live inside a collapsed "Settings & tools" accordion; real features (Warm path, Boosters, Company brief) are mislabeled as settings.
7. **Header inconsistency**: only 7 pages use `PageHeader`; the rest hand-roll `<h1>`s; dashboard uses a different scale.
8. **Content width jumps between pages** (max-w-2xl → 3xl → 4xl → 5xl → 6xl with no rule).
9. **Developer commands shown to end users**: DB banner tells users to run `npm run db:up` / `prisma migrate dev`. A non-technical user is stranded.
10. **Instrumentation as UI**: "OpenRouter probe", DB latency, ghosts/scams/dupes counters, adapter live/mock badges on the dashboard. Move behind a diagnostics page.

Minor: no "system" theme option in the toggle; 10px muted text likely fails AA contrast; `not-found`/error CTA style mismatch.

## 5. Installation & lifecycle strategy (OMP-style comparison)

Oh My Posh's model: one-line script or package-manager install of a single self-contained binary, a CLI entry point (`oh-my-posh init`), and built-in `upgrade`/notice-based self-update. The question is which parts transfer to an app that needs Node, Next.js, and Postgres+pgvector.

**A. Script installer (`curl | bash` / `install.ps1`)**
- How: script checks Node/Docker, clones or downloads a release tarball, installs deps, runs migrations, writes launchd agents, opens the browser.
- User XP: one command, familiar to devs; scary and opaque to non-technical users; breaks differently on every machine (PATH, permissions, corporate proxies).
- Dev XP: cheap to write, expensive to keep working across macOS versions/shells.
- Breaks: partial installs with no rollback; silent Docker absence; PATH issues.
- Verdict: fine as a *bootstrap convenience* on top of another mechanism, not as the mechanism.

**B. Package manager (Homebrew tap)**
- How: formula/cask installs a launcher; deps declared (node, optionally colima/postgres).
- User XP: `brew install job-os` is the cleanest CLI story; `brew upgrade` gives updates for free.
- Dev XP: maintaining a tap + release automation is ongoing work; Homebrew can't manage your Postgres data lifecycle or launchd agents well; brew-installed background services confuse users.
- Breaks: brew-updated Node major versions; formula drift.
- Verdict: good *distribution channel* for the CLI launcher once one exists; doesn't solve first-run or DB lifecycle by itself.

**C. CLI launcher (`jobos` command — the OMP-analogous piece)**
- How: a small CLI (Node/tsx or a compiled binary) with subcommands: `jobos doctor` (preflight: Node version, Docker running, ports free, migrations pending), `jobos start` (db up → migrate deploy → server → open browser, with port fallback), `jobos stop`, `jobos backup`, `jobos update` (pull/download, install, migrate, restart), `jobos logs`.
- User XP: one memorable command; failures become readable messages instead of stack traces.
- Dev XP: consolidates the currently scattered logic (README steps, db-banner commands, install-agents, catchup) into one tested place. This directly fixes issues §3.4, §3.6, §3.8, §3.9.
- Breaks: little — it wraps things that exist. Chief risk is drift if docs keep advertising raw npm scripts alongside it.
- Verdict: **highest value per effort. Do this regardless of the packaging endpoint.**

**D. Desktop launcher (Tauri app)**
- How: finish the scaffold — fix the standalone path, bundle a Node runtime as `externalBin` (or migrate the server to a sidecar binary), embed Postgres alternatives (see below), add the Tauri updater.
- User XP: best possible for non-technical users — double-click, no terminal ever. Matches your stated "premium, exclusive product" goal and README's stated primary target.
- Dev XP: heaviest: code signing/notarization, updater infrastructure, and the hard problem — **Postgres+pgvector inside a desktop app**. Options: bundle embedded Postgres binaries (~40MB, doable), or swap to PGlite (pgvector supported, no Docker, but Prisma support is still maturing), or keep requiring Docker (kills the non-technical UX).
- Breaks: signing/notarization pipeline; sidecar crashes; DB engine swap risk.
- Verdict: the right *end state*, but it's a milestone, not a quick fix.

**E. Background service (launchd) for the server itself**
- How: run the Next server as a KeepAlive launchd agent; app is "always on" at localhost:3000.
- User XP: instant loads, scheduler always current; but invisible resource use and confusing "how do I turn it off".
- Dev XP: simple to add via the existing `launchd.ts` generator; log/rotation and crash-loop handling needed.
- Verdict: good *option* managed by the CLI (`jobos service install`), not the default.

**F. Self-update**
- How: `jobos update` (CLI path) and Tauri updater (desktop path); on every start, auto-run `prisma migrate deploy` so schema can never drift from code (fixes §3.5).
- Risks: failed mid-update states — mitigate by backing up (you already have encrypted backups) before migrating.

**Recommendation:** C now, D as the destination, B as distribution for C, A only as a thin bootstrap for C, E optional behind C, F built into both. Concretely: build the `jobos` CLI with `doctor`/`start`/`update` this month; it immediately makes today's dev-hosted app feel like a product, and every piece of it (preflight, migrate-on-start, port fallback) is reused verbatim by the Tauri shell later.

## 6. Prioritized improvement plan

Format: what / why / benefit / complexity / risks / order.

### P0 — This week (safety + hang prevention)
1. **Rotate the leaked keys and scrub `.env`.** Active credentials in cleartext. Benefit: closes the highest blast-radius issue. Complexity: trivial. Risk: none.
2. **Shared `fetchWithTimeout` applied to all job sources, Gmail, and AI calls; default 10–15s abort.** Why: single hung vendor currently stalls everything. Benefit: app can no longer hang on network. Complexity: low (pattern already exists in `safeFetch`). Risk: legitimate slow responses cut off — make timeout configurable.
3. **Configure the pg Pool (`max`, `connectionTimeoutMillis`, `idleTimeoutMillis`, `statement_timeout`) and add `pool.on('error')`.** Why: unhandled idle-client error can crash the process. Complexity: trivial. Risk: none.
4. **Fix migration guidance**: banner + `db:migrate` → `prisma migrate deploy` for apply, keep `migrate dev` as a separate dev-only script. Complexity: trivial.

### P1 — Next 2 weeks (reliability + honest UI)
5. **Overlap lock for catchup/discover** (pidfile or Postgres advisory lock) + failure backoff on watermarks + surface `lastStatus` failures in `SystemReadiness`. Benefit: no double spend, no silently masked outages. Complexity: low-medium.
6. **Dedupe/cache job embeddings; parallelize ingest with a concurrency limit (~4).** Benefit: 3× fewer AI calls, ingest minutes → seconds. Complexity: medium. Risk: rate limits — keep the limit conservative.
7. **Replace fixture-substitution with real empty states.** Preview data only when DB is *down*, labeled loudly; healthy-empty shows a CTA ("Run your first discovery"). Benefit: trust + first-run clarity. Complexity: low.
8. **Per-route `loading.tsx` skeletons** for jobs, track, setup, dashboard. Benefit: biggest perceived-quality win. Complexity: low.
9. **Global toast + route all server actions through `useActionFeedback`.** Complexity: medium.
10. **Atomic secrets writes** (write-temp-then-rename with a simple in-process mutex). Complexity: low.

### P2 — Next month (lifecycle + product feel)
11. **Build the `jobos` CLI** (doctor / start with port fallback / stop / update / logs / service install), auto-`migrate deploy` on start, create `.logs/` in installer, add `engines` + `.nvmrc`. Benefit: reliable launch on any machine; turns the DB banner into "Job OS will fix this" instead of npm commands. Complexity: medium. This is the OMP-style backbone.
12. **Navigation restructure**: promote real features out of the "Settings & tools" accordion; standardize `PageHeader` and one content width; move instrumentation (probes, adapter badges, funnel internals) to a Diagnostics page. Complexity: medium.
13. **Accessibility pass**: `prefers-reduced-motion`, contrast check on small muted text, system theme option. Complexity: low.
14. **Zod validation for all mutating server actions** + move webhook token out of query string. Complexity: medium, mechanical.
15. **Job staleness policy**: mark/hide postings older than N days, prune excluded/dead rows, add User-Agent to RemoteOK. Complexity: low.

### P3 — The desktop milestone
16. **Fix Tauri**: correct standalone path, bundle Node (or sidecar binary), decide the DB story (embedded Postgres vs PGlite vs Docker requirement), surface sidecar stderr, add the Tauri updater with pre-update backup. Benefit: the actual "premium product" experience. Complexity: high. Risks: signing/notarization, DB engine migration. Do only after P0–P2, reusing the CLI's preflight/start logic.

### Sequencing logic
P0 removes crash/hang/credential risk with almost no code. P1 makes behavior honest and fast. P2 makes it operable by a non-technical user. P3 packages it. Skipping ahead to P3 first would package today's fragility.

## 7. Assumptions worth challenging

- **Postgres+pgvector via Docker is the single biggest obstacle to the product you describe.** For a single-user local app, evaluate PGlite or embedded Postgres seriously; Docker is the #1 reason non-technical installs fail.
- **Fixture-preview-everywhere** was clearly a dev convenience; as a product default it undermines trust. Fixtures should be a demo mode, explicitly toggled.
- **60+ bespoke `test:*` tsx scripts** instead of a test runner (vitest) means no single pass/fail gate, no CI-friendly output, and scripts that rot silently. Consolidate.
- **Two build caches + three tsbuildinfo files in the repo root** hint at accumulated workarounds; the CLI should own cache hygiene (`jobos doctor --fix`).
- **LAN hosting "supported equally"** but token entry UI is deferred — either finish it or de-scope LAN from the README promise.
